# 🔥 Campfire

ห้องคุยเสียงแบบ peer-to-peer ที่อยู่ในไฟล์ HTML ไฟล์เดียว — ไม่ต้องติดตั้ง ไม่ต้องสมัคร ไม่มีเซิร์ฟเวอร์เก็บอะไรไว้

ก่อกองไฟ ชวนเพื่อนมานั่งล้อมวง พอคนสุดท้ายออกจากห้อง กองไฟก็ดับไปพร้อมกัน

---

## ใช้ยังไง

### แบบเร็วสุด — เปิดจากไฟล์ (คอมเท่านั้น)

1. ส่งไฟล์ `index.html` ให้เพื่อนทุกคน (Discord / LINE / อีเมล อะไรก็ได้)
2. ทุกคนดับเบิลคลิกเปิดไฟล์ในเบราว์เซอร์
3. ใส่ชื่อตัวเอง + **ชื่อห้องที่ตกลงกันไว้ให้ตรงกันเป๊ะ ๆ**
4. กด "เข้าห้อง" แล้วกด "อนุญาต" ตอนเบราว์เซอร์ขอใช้ไมค์
5. **ไมค์จะปิดไว้ก่อน** กดปุ่มไมค์หรือปุ่ม `M` เมื่อพร้อมพูด

ใครพิมพ์ชื่อห้องเหมือนกันจะเจอกัน ไม่มีระบบสมาชิกหรือรหัสผ่าน — **ชื่อห้องคือรหัสผ่านในตัว** ถ้าไม่อยากให้ใครหลงเข้ามาก็ตั้งชื่อให้เดายาก

### แบบมีลิงก์ — ต้องทำถ้าจะใช้บนมือถือ

> ⚠️ **iPhone / iPad เปิดจากไฟล์ไม่ได้** — Safari บน iOS ไม่ยอมให้เว็บที่เปิดจากไฟล์ในเครื่องใช้ไมค์ ต้องเป็นลิงก์ `https://` เท่านั้น (Android ก็เจอปัญหาคล้ายกันในบางเบราว์เซอร์)

วิธีที่เร็วที่สุด — **Netlify Drop** (~2 นาที ทำจากคอม ไม่ต้องตั้งค่าอะไร):

1. สร้างโฟลเดอร์เปล่า เอา `index.html` ใส่เข้าไปไฟล์เดียว
2. เปิด <https://app.netlify.com/drop> แล้วลากโฟลเดอร์เข้าไป
3. ได้ลิงก์ `https://xxx.netlify.app` มาทันที ส่งลิงก์นี้ให้เพื่อน เปิดได้ทุกเครื่อง

หรือถ้ามี GitHub อยู่แล้ว — **GitHub Pages**:

1. สร้าง repo สาธารณะ อัป `index.html` เข้าไป
2. Settings → Pages → Branch `main` → Save
3. รอสักครู่ จะได้ `https://<user>.github.io/<repo>/`

> โฮสต์อะไรก็ได้ที่เสิร์ฟเป็น HTTPS — ไม่ต้องมี backend เพราะทั้งแอปคือไฟล์ static ไฟล์เดียว

## มีอะไรบ้าง

| ฟีเจอร์ | รายละเอียด |
|---|---|
| เปิด/ปิดไมค์ | ปุ่มกลาง หรือกด `M` — ปิดที่ตัว audio track จริง ไม่ใช่แค่ไอคอน |
| ปิดเสียงทุกคน | ปุ่มลำโพง หรือกด `D` |
| เห็นว่าใครพูด | ขอบการ์ดและวงรอบตัวอักษรเรืองแสงสีไฟตามเสียงจริง (วิเคราะห์ในเครื่อง ไม่ได้ส่งข้อมูลอะไรเพิ่ม) |
| ปรับเสียงรายคน | สไลเดอร์ข้างชื่อแต่ละคน ปรับเฉพาะที่เครื่องเรา |
| แชทข้อความ | วิ่ง P2P ตรงถึงทุกคนเหมือนเสียง พร้อมบอกว่าใครเข้า/ออกห้อง — ไม่เก็บลงที่ไหน |
| ตัดเสียงรบกวน | Noise gate ปิดไมค์อัตโนมัติตอนไม่ได้พูด พร้อมมิเตอร์และสไลเดอร์ปรับความไว (ดูหัวข้อด้านล่าง) |
| เลือกไมค์ | สลับไมค์/หูฟังได้กลางคันโดยไม่ต้องออกห้อง จำค่าที่เลือกไว้ให้ครั้งหน้า |
| เชิญออกจากห้อง | เจ้าของห้องไล่คนออกได้ ต้องกดยืนยันสองครั้ง — ทุกเครื่องตัดสายกับคนนั้นเอง |
| เจ้าของห้องหลุด | คนที่เหลือรับช่วงต่ออัตโนมัติใน ~10 วินาที เสียงที่กำลังคุยอยู่ไม่ขาด |

**ปุ่มลัด:** `M` เปิด/ปิดไมค์ · `D` ปิดเสียงทุกคน

**หน้าตา:** เต็มจอ ไม่เลื่อนทั้งหน้า — รายชื่อคนอยู่บน (ยาวเกินก็เลื่อนในกรอบตัวเอง) แชทกินพื้นที่ที่เหลือทั้งหมด แถวปุ่มติดอยู่ล่างจอตลอด และการตั้งค่า (ไมค์ + noise gate) ซ่อนอยู่ในปุ่มเฟือง

**เหมาะกับ 2–6 คน** — ทั้งเสียงและแชทเป็น full mesh (ทุกคนต่อตรงหากันหมด) จำนวนสายโตแบบ N(N−1)/2 สองชุด: 4 คน = 6+6 สาย, 6 คน = 15+15 สาย, 8 คน = 28+28 สาย และแต่ละคนต้อง**เข้ารหัสเสียงส่งออกแยกกันทีละคน** ทำให้ทั้งแบนด์วิดท์ขาขึ้นและ CPU โตตามจำนวนคน

ทดสอบแล้ว: **6 คนทำงานครบถ้วน** (mesh ครบทุกคู่ แชทถึงกันครบ) ส่วน 8 คนขึ้นไปยังไม่มีผลวัดที่เชื่อถือได้ เพราะเครื่องที่ใช้ทดสอบเองรับ 8 เบราว์เซอร์พร้อมกันไม่ไหว

**จำกัดที่ 8 คน** (`MAX_PEERS`) และเริ่มเตือนเป็นสีไฟตั้งแต่ 6 คน — เหตุผลไม่ใช่เรื่องประสิทธิภาพล้วน ๆ แต่เป็นเรื่อง**รูปแบบความพัง**: ถ้าปล่อยให้เข้าเกิน มันจะไม่ขึ้น error อะไรเลย แต่บางคู่ต่อกันไม่ติดแบบเงียบ ๆ (A ได้ยิน B แต่ไม่ได้ยิน C ส่วน C ได้ยินทุกคน) ซึ่งหาสาเหตุยากกว่าข้อความ "ห้องเต็ม" ตรง ๆ มาก

## ทำงานยังไง

### ภาพรวม

```
              ┌──────────────────────┐
              │   0.peerjs.com       │  ← แค่พาสองเครื่องมาเจอกันตอนแรก
              │   (signaling)        │     ไม่มีเสียงวิ่งผ่านตรงนี้
              └──────────────────────┘
                   ▲     ▲     ▲
                   │     │     │   (WebSocket ตอน handshake เท่านั้น)
              ┌────┴─┐ ┌─┴───┐ ┌┴────┐
              │  A   │◄┤  B  ├►│  C  │
              └──┬───┘ └─────┘ └───┬─┘
                 └─────────────────┘
                   เสียงวิ่งตรงระหว่างเครื่อง (WebRTC)
```

เสียงไม่เคยผ่านเซิร์ฟเวอร์ใคร เซิร์ฟเวอร์ signaling มีหน้าที่แค่แลก SDP/ICE ตอนเริ่มต้นเท่านั้น

### ชื่อห้อง → peer id

ชื่อห้องถูก slug + hash (djb2) เป็น id คงที่ เช่น `microom-v1-kuan-game-1x9k2p`

- **เจ้าของห้อง (host)** คือคนที่จองชื่อ id นั้นบนเซิร์ฟเวอร์ signaling ได้ — ใครเข้ามาก่อนได้เป็น
- **คนอื่น ๆ** ใช้ id แบบ `microom-v1-kuan-game-1x9k2p-u<สุ่ม>` แล้วต่อ data connection ไปหา host

host ทำหน้าที่เป็น **สมุดรายชื่อ** อย่างเดียว ไม่ได้เป็นตัวกลางส่งเสียง — พอรู้รายชื่อกันแล้วทุกคนโทรหากันเองตรง ๆ

### กติกาที่ทำให้ไม่ต่อซ้ำซ้อน

ทุกคู่จะมี media connection เดียว โดยให้ **ฝั่งที่ peer id เรียงน้อยกว่าเป็นคนโทรออก** อีกฝั่งรอรับอย่างเดียว

### แชท

ข้อความไม่ได้วิ่งผ่าน host เลย — แต่ละคนเปิด **DataConnection ตรงถึงกันทุกคู่** (data mesh) โดยใช้กติกา "id น้อยกว่าเป็นคนเปิดสาย" เดียวกับเสียง ส่งทีเดียวถึงทุกคนพร้อมกัน ไม่ต้อง relay ไม่ต้องกันข้อความซ้ำ

- ข้อความ **ไม่ถูกเก็บที่ไหนเลย** ไม่ใช่แค่ไม่มีเซิร์ฟเวอร์ — ในเครื่องก็ไม่เก็บ ปิดแท็บคือหายหมด
- คนที่เข้ามาทีหลัง **ไม่เห็นข้อความย้อนหลัง** เป็นความตั้งใจ ไม่ใช่ข้อจำกัด — เข้ากับแนวคิดที่ว่ากองไฟดับแล้วไม่เหลืออะไร
- ป้ายบอก "ใครเข้า/ออกห้อง" คำนวณจากการเทียบรายชื่อในเครื่องตัวเอง ไม่ได้ส่งข้อความเพิ่มสักไบต์
- ข้อความจากคนอื่นถูกใส่ด้วย `textContent` เสมอ ไม่เคยแตะ `innerHTML` — ส่ง HTML หรือสคริปต์มาก็ขึ้นเป็นตัวหนังสือธรรมดา
- ชื่อผู้ส่งยึดจาก id ของสายที่ข้อความวิ่งเข้ามา ไม่เชื่อชื่อที่แนบมาในตัวข้อความ จึงปลอมเป็นคนอื่นไม่ได้

### เชิญออกจากห้อง (kick)

สิทธิ์อยู่ที่ **เจ้าของห้องคนปัจจุบัน** เท่านั้น — คนที่ถือ id ของห้องอยู่ ไม่ใช่ใครที่เข้ามาก่อน (ถ้าเจ้าของห้องหลุดแล้วมีคนรับช่วงต่อ สิทธิ์ก็ย้ายไปด้วย)

ขั้นตอนตอนกดไล่ออก:

1. ปุ่มต้องกดสองครั้ง ครั้งแรกเปลี่ยนเป็น "ยืนยัน?" และคืนสภาพเองใน 4 วินาที — กันกดพลาด
2. host ส่ง `{t:"kicked"}` ไปที่สายของคนนั้นโดยตรง แล้วตัดสาย
3. เอาออกจากรายชื่อและ broadcast ให้ทุกคน — สายเสียงกับสายแชทของคนอื่นจะถูกเก็บกวาดเอง
4. id นั้นถูกใส่ **banlist** ของ host กันต่อกลับเข้ามาด้วย id เดิม
5. ฝั่งคนที่ถูกไล่ ตัดทุกสายแล้วขึ้นหน้าบอก ไม่พยายามต่อกลับเอง

6. ทุกเครื่อง**ปฏิเสธสายที่คนนั้นต่อกลับเข้ามาเอง** — เสียงจะไม่ถูกเล่นและข้อความจะถูกทิ้ง ถ้าคนส่งไม่อยู่ในรายชื่อห้อง

ข้อ 6 สำคัญกว่าที่คิด: คนที่ถูกไล่ออก**จำ peer id ของทุกคนได้จากตอนที่ยังอยู่ในห้อง** ถ้ารับสายเข้าโดยไม่เช็กรายชื่อ เขาจะต่อกลับมายิงเสียงและแชทใส่ได้ตรง ๆ โดยไม่ต้องผ่าน host เลย (ทดสอบแล้วว่าเป็นไปได้จริงก่อนแก้) ตอนนี้ตัวตัดสินคือ**รายชื่อห้อง ไม่ใช่ว่าใครต่อสายมา**

**จุดแข็ง:** การถูกไล่ออกไม่ได้พึ่งความร่วมมือของเครื่องคนที่ถูกไล่เลย — พอหลุดจากรายชื่อ ทุกเครื่องจะตัดสายเสียงและสายแชทกับเขาเองผ่าน `reconcile()` ต่อให้เขาแก้ HTML ให้ไม่แสดงหน้าแจ้ง ก็ไม่มีใครได้ยินเสียงและไม่มีใครเห็นข้อความเขาอยู่ดี

**จุดอ่อนที่ต้องรู้:** banlist เก็บเป็น peer id ซึ่ง**สุ่มใหม่ทุกครั้งที่โหลดหน้า** — คนที่ถูกไล่กด F5 แล้วเข้ามาใหม่ได้ และ banlist อยู่ในหน่วยความจำของ host เท่านั้น ถ้า host ปิดแท็บแล้วมีคนรับช่วงต่อก็หายไปด้วย ให้คิดว่า kick คือ **"เชิญออก" ไม่ใช่ "แบน"**

### สายไหนสั่งอะไรได้บ้าง

ในห้องมีสายข้อมูลสามประเภท และ **แต่ละประเภทส่งได้เฉพาะข้อความของตัวเอง** — บังคับที่ฝั่งผู้รับ ไม่ใช่ฝั่งผู้ส่ง

| สาย | ใครถึงใคร | ส่งได้เฉพาะ |
|---|---|---|
| `member` | สมาชิก → host | `hello` `state` `ping` |
| `host` | host → สมาชิก | `roster` `kicked` `full` `badver` |
| `chat` | สมาชิก ↔ สมาชิก | `chat` เท่านั้น |

จุดสำคัญคือ**สายแชทสั่งอะไรเกี่ยวกับห้องไม่ได้เลย** ก่อนหน้านี้ตัวรับข้อความใช้ตัวเดียวกันหมดโดยไม่ดูว่ามาจากสายไหน ผลคือสมาชิกที่แก้ HTML เองสามารถยิง `kicked` ไล่สมาชิกคนอื่น หรือยิง `roster` เขียนรายชื่อในจอคนอื่นทับได้ ตอนนี้ปิดแล้ว และ `kicked` กับ `roster` ยังต้องมาจากสายที่ต่อกับ host จริง ๆ (`conn === hostConn`) ซ้ำอีกชั้น

**ขอบเขตที่กันไม่ได้:** แอปรันฝั่ง client ล้วน ไม่มีเซิร์ฟเวอร์ตัดสิน ใครมีไฟล์อยู่ในมือก็แก้ได้ ปลอมชื่อซ้ำคนอื่นก็ได้เพราะไม่มีระบบ identity — ถ้าต้องการของที่กันได้จริงต้องมีเซิร์ฟเวอร์ถือสิทธิ์ ซึ่งขัดกับคอนเซปต์ของแอปนี้

### ทำไมถึงไม่ verify ว่าทุกคนรันโค้ดชุดเดียวกัน

เคยคิดจะให้แต่ละคน hash โค้ดทั้งไฟล์แล้วส่งให้ host ตรวจ — **ใช้ไม่ได้ และตั้งใจไม่ทำ**

สิ่งนั้นเรียกว่า remote attestation ซึ่งต้องมี root of trust ที่ผู้ใช้แก้ไม่ได้ (TPM, Secure Enclave, เซิร์ฟเวอร์) ในเบราว์เซอร์ไม่มี — **โค้ดที่คำนวณ hash ก็คือโค้ดที่ผู้โจมตีควบคุมอยู่** แก้เป็น `send({hash:"ค่าที่ถูกต้อง"})` จบ ต่อให้ใส่ nonce กันรีเพลย์ ก็เก็บสำเนาโค้ดต้นฉบับไว้ hash ตัวนั้นแทนได้ แถมยังมีผลเสียจริงคือ hash เปลี่ยนทุกครั้งที่แก้ CSS ทำให้คนที่ไฟล์ต่างกันนิดเดียวเข้าห้องไม่ได้ทั้งที่โปรโตคอลเข้ากันได้

หลักที่ใช้แทนคือ **ความลับได้ผล การพิสูจน์ตัวตนของโค้ดไม่ได้ผล** เพราะฉะนั้นอย่าพยายามแยกโค้ดดีออกจากโค้ดร้าย แต่ออกแบบให้**ต่อให้เป็นโค้ดร้ายก็ทำอะไรไม่ได้**:

| กลไก | ได้ผลจริงไหม | เพราะอะไร |
|---|---|---|
| แยกสิทธิ์ตามประเภทสาย | ✅ | บังคับที่ฝั่งผู้รับ ซึ่งเป็นโค้ดที่เราคุมเอง |
| rate limit แชท | ✅ | เหมือนกัน — ผู้ส่งแก้โค้ดยังไงก็ไม่ช่วย |
| จำกัดจำนวนคน | ✅ | host ถือสมุดรายชื่อ คนที่ถูกปฏิเสธไม่รู้ peer id ของใครเลย ต่อเข้ามาไม่ได้ |
| ปฏิเสธสายจากคนนอกรายชื่อ | ✅ | ตัวตัดสินคือรายชื่อห้อง ไม่ใช่ว่าใครต่อสายเข้ามา |
| ตัดจำนวนรายชื่อที่รับ | ✅ | host ที่ถูกแก้โค้ดส่งรายชื่อมาเป็นแสนก็ทำเครื่องเราค้างไม่ได้ |
| ป้ายรหัสเวลาชื่อซ้ำ | ✅ | ปลอมชื่อได้ แต่ปลอม peer id ไม่ได้ |
| เลขรุ่นโปรโตคอล | ⚠️ | มีไว้กันไฟล์คนละรุ่นพังเงียบ ๆ **ไม่ใช่มาตรการความปลอดภัย** — แก้เลขให้ตรงก็ผ่าน |
| banlist | ⚠️ | กันได้แค่ id เดิม รีเฟรชแล้วได้ id ใหม่ |
| hash โค้ด | ❌ | ผู้โจมตีส่ง hash อะไรก็ได้ |

### จำกัดความถี่ข้อความ

ฝั่งผู้รับนับข้อความต่อคน เกิน **10 ข้อความใน 10 วินาที** จะเมินส่วนเกินแล้วขึ้นป้ายบอกครั้งเดียวต่อ 30 วินาที (ไม่งั้นป้ายเตือนจะกลายเป็นสแปมเสียเอง) ทดสอบแล้ว: ยิง 15 ข้อความรวด ผู้รับเห็น 10

### Heartbeat & การรับช่วงต่อ

- host broadcast รายชื่อทุก **3 วินาที** สมาชิกส่ง ping กลับทุก 3 วินาที
- ตัวตัดสินหลักว่าใครหลุดคือ **สถานะของสายเอง** (`conn.open`, `connectionState`) ไม่ใช่นาฬิกา — เพราะ**เบราว์เซอร์หรี่ `setInterval` ของแท็บที่ไม่ได้อยู่หน้าจอ** ถ้าไปตัดคนจากการที่ ping ขาด คนที่สลับไปเล่นเกมอยู่อีกแท็บจะโดนเตะออกทั้งที่เสียงยังดีอยู่
- host ตัดสมาชิกเมื่อ **สายปิดแล้วและเงียบเกิน 8 วินาที** หรือเงียบสนิทเกิน **60 วินาที** (ตัวสำรองกันสายซอมบี้)
- สมาชิกถือว่า host หายเมื่อสายไปหา host อยู่ในสถานะ `failed`/`closed` หรือไม่ได้รับรายชื่อเกิน **45 วินาที** แล้วแย่งกันจอง id ห้องใหม่ด้วย random backoff (0.8–3 วินาที)
- วัดจริง: host ปิดแท็บไป → คนที่เหลือรับช่วงต่อใน **~20 วินาที** โดยเสียงที่ต่ออยู่แล้วไม่ขาด
- สายที่ **เปิดไม่ติด** จะถูกทิ้งหลัง 8 วินาที (สายแชท) / 15 วินาที (สายเสียง) เพื่อให้รอบ retry ต่อใหม่ได้ — ถ้าปล่อยค้างไว้ รอบ retry จะเห็นว่า "มีสายแล้ว" แล้วไม่ต่อใหม่ตลอดกาล กลายเป็นเงียบไปเฉย ๆ แบบไม่มีสัญญาณเตือน

ระหว่างเปลี่ยนมือ **เสียงที่ต่ออยู่แล้วไม่ขาด** เพราะ WebRTC connection เป็นอิสระจาก signaling

### ตัดเสียงรบกวน

มีสองชั้นซ้อนกัน

**ชั้นแรก — DSP ของเบราว์เซอร์** เปิดไว้ตลอดตอนขอใช้ไมค์:

```js
{ echoCancellation: true, noiseSuppression: true, autoGainControl: true }
```

จัดการเสียงที่ดังต่อเนื่องคงที่ (พัดลม แอร์ เสียงซ่า) กันเสียงวนจากลำโพง และปรับความดังให้สม่ำเสมอ

**ชั้นสอง — Noise gate** เขียนเองด้วย Web Audio เพื่อตัดสิ่งที่ชั้นแรกทำไม่ได้ คือเสียงเป็นจังหวะอย่างคีย์บอร์ดหรือเสียงคนข้าง ๆ **ในช่วงที่เราไม่ได้พูด**

```
ไมค์ ──┬──► AnalyserNode ──► วัดระดับเสียง (ก่อนถูกตัด)
       │
       └──► GainNode (ประตู) ──► MediaStreamDestination ──► ส่งออกให้เพื่อน
```

- วัดระดับจาก**ก่อน**ประตู เพื่อให้ยังรู้ว่าเริ่มพูดแล้วแม้ประตูกำลังปิดอยู่
- เกินเกณฑ์ → เปิดประตู ramp 10 ms (เร็วพอที่จะไม่กินคำแรก)
- เงียบลง → ค้างเปิดไว้อีก 350 ms แล้วค่อยปิดแบบ ramp 120 ms (ไม่กินคำท้ายประโยค ไม่มีเสียงกึก)
- ปิดไมค์ = สั่ง `enabled = false` ทั้งฝั่งดิบและฝั่งที่ส่งออก ไม่ได้พึ่งประตูอย่างเดียว

ผลพลอยได้: track ที่ส่งออกคือปลายทางของสาย ไม่ใช่ track ของไมค์โดยตรง เลย**สลับไมค์กลางคันได้โดยไม่ต้อง renegotiate** กับใครเลย — แค่ต่อต้นทางใหม่เข้าสายเดิม

ถ้าเบราว์เซอร์ทำ Web Audio ไม่ได้ จะถอยไปส่งเสียงดิบตรง ๆ แทน (แล้วค่อยใช้ `replaceTrack` ตอนสลับไมค์)

## ข้อจำกัดที่รู้อยู่

- **iOS ต้องเปิดผ่าน HTTPS** เท่านั้น (ดูหัวข้อด้านบน)
- **พึ่งเซิร์ฟเวอร์ signaling สาธารณะ** — `0.peerjs.com` เป็นบริการฟรีที่ไม่มีใครรับประกัน ถ้าล่มก็เข้าห้องใหม่ไม่ได้ (ห้องที่ต่อกันอยู่แล้วยังคุยได้ต่อ) ถ้าจะใช้จริงจังควร self-host PeerServer
- **ไม่มีการเข้ารหัสระดับแอป** — WebRTC เข้ารหัส DTLS-SRTP ให้อยู่แล้วระหว่างทาง แต่ใครรู้ชื่อห้องก็เข้ามาได้
- **TURN สาธารณะไม่การันตี** — ถ้า openrelay ล่มและเน็ตทั้งสองฝั่งเป็น NAT โหด อาจต่อกันไม่ติด
- **ยังไม่ได้ทดสอบกับเซิร์ฟเวอร์ signaling ตัวจริง** — logic ทั้งหมด (mesh 3 เครื่อง, การรับช่วงต่อ, สถานะไมค์) ทดสอบผ่านด้วย PeerServer ที่รันในเครื่อง
